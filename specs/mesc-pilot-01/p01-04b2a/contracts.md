## Canonical value domain

`CanonicalJsonValue` permits only:

- `null`
- boolean
- UTF-8 string
- unbounded integer
- ordered array of `CanonicalJsonValue`
- string-keyed object mapping UTF-8 strings to `CanonicalJsonValue`

Binary floating-point values are prohibited in fingerprinted promotable
payloads. Later numeric requirements must use integer, versioned fixed-point,
or canonical decimal-string representation frozen by contract.

Object keys must be strings. Non-string object keys are rejected.

### Boolean and integer are distinct types

Boolean and integer are distinct types within the canonical value domain. Both
remain permitted values, but they are never interchangeable:

- A boolean is never accepted where an integer is required, including
  `byte_size`.
- An integer is never accepted where a boolean is required.
- Implementations must not treat `bool` as a subtype of integer, and must not
  rely on any language-level subtyping that would admit a boolean wherever an
  integer is required.
- Violations fail closed with `unsupported_value_type`.

This rule is normative and is stated identically in `decision-record.md` under
PD-B2A-2. It does not alter the permitted value domain above and does not alter
the prohibition on binary floating-point values.

## Canonical JSON and JSONL rules

- UTF-8 only; no BOM.
- Recursive lexicographic key ordering.
- `ensure_ascii=False`; `allow_nan=False`.
- Compact separators `(",", ":")`; no indentation.
- LF only; no CRLF.
- A single JSON object ends in exactly one LF.
- JSONL records are one object per line, each ending in exactly one LF.
- No blank lines.
- Zero JSONL records produce zero bytes.
- Record order is supplied by the caller and must already be deterministic.
- Serializers return bytes only and perform no filesystem I/O.

## Artifact descriptors

`SplitArtifactRole` is a finite enumerable string. Later addition of an
unknown role fails closed unless a new bundle schema version is ratified.

`SplitArtifactDescriptor` is immutable and contains:

- `role`
- `schema_version`
- `sha256`
- `byte_size`

Rules:

- `sha256` is exactly 64 lowercase hexadecimal characters.
- `byte_size` is a non-negative integer.
- Duplicate roles fail closed.
- Missing required roles fail closed.
- Unknown roles fail closed unless a new bundle schema version is ratified.

Required B2A artifact roles:

- `group_registry`
- `example_registry`
- `split_summary`
- `excluded_ledger`

Leakage reports are not part of B2A and must not be added to the required
role set.

`SplitArtifactDescriptor` ordered canonical sort key:
`role` ascending.

## Identity models

`SplitFingerprintIdentity` is the canonical fingerprinted payload and
contains:

- bundle schema version;
- policy identifier;
- split algorithm version;
- split seed/domain separator;
- ordered artifact descriptors;
- split-summary identity core.

It must not contain:

- `split_fingerprint`;
- dates or timestamps;
- paths;
- usernames;
- hostnames;
- runtime versions;
- command logs;
- environment data.

`SplitFingerprintRecord` contains:

- the complete identity payload;
- computed `split_fingerprint`.

Definition:

```
split_fingerprint = SHA-256(canonical single-object JSON bytes of SplitFingerprintIdentity)
```

The exact terminal LF generated by the canonical serializer is part of the
hashed bytes.

Authoritative fingerprint:
full 64-hex SHA-256.

B1 16-hex `split_hash` remains display/compatibility-only and must not be
used as B2A authority.

## Split-summary identity core

`SplitSummaryIdentityCore` may contain only deterministic aggregate facts
needed to bind the split:

- total example count;
- total source-document/group count;
- partition totals;
- aggregate label totals;
- aggregate partition-by-label matrix;
- group counts by partition;
- excluded-record count;
- algorithm and schema identities when not already represented at the bundle
  level.

It must not contain:

- per-example answer labels;
- raw question/context text;
- dates or timestamps;
- the authoritative fingerprint itself;
- runtime provenance.

D9 remains controlling.

- `split_summary`: `mesc-pilot-01-split-summary-identity-core/1`

Exactly one role-compatible schema version is valid for each role in version 1.
Role or version mismatch fails closed. Empty, malformed, unknown, and
unsupported versions fail closed. Another role or version requires a newly
ratified bundle schema. All such failures use `invalid_schema_version`.

## Canonical key order

Object keys are sorted by ascending Unicode code-point sequence using direct,
case-sensitive string comparison.

Ordering is not locale-aware, case-folded, normalized, filesystem-derived, or
insertion-order-derived.

Strings that cannot be encoded as valid UTF-8 must fail closed with:
`canonicalization_failure`

## Non-circular fingerprint proposal

The following behavior is proposed as a pending founder decision and is not
authoritative until explicitly ratified.

- `split_summary` descriptor hashes only canonical bytes of `SplitSummaryIdentityCore`.
- Those bytes exclude `split_fingerprint`, authoritative use of B1 `split_hash`, dates, timestamps, provenance, runtime metadata, paths, hostnames, usernames, command logs, and environment data.
- `SplitFingerprintRecord` is produced only after the fingerprint is calculated.
- `SplitFingerprintRecord` is not one of its own four fingerprint inputs.
- A display or final summary may include the computed fingerprint after calculation, but its final bytes are not recursively fingerprinted.

Proposed validation sequence:

1. Canonicalize fingerprint-free `SplitSummaryIdentityCore`.
2. Calculate its `split_summary` descriptor.
3. Validate all four required descriptors.
4. Construct `SplitFingerprintIdentity`.
5. Canonicalize that identity.
6. Compute the full SHA-256 fingerprint.
7. Construct `SplitFingerprintRecord`.
8. Recompute all bound hashes, byte sizes, and final fingerprint during verification.
9. Reject every mismatch.
