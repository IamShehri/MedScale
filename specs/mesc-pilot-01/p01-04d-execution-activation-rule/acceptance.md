### 1.1 Scope basis

The package is confined to three new documentation paths because the decision it
records is self-contained: it defines a rule that a *future* package must follow,
and it changes no current status that an existing canonical record asserts.

Two earlier P01-04D governance packages carried a `specs/mesc-pilot-01/tasks.md`
ledger block in their change scope. The most recent canonically adopted P01-04D
governance package did not: the ledger's final block is `P01-T03D3`, recording
the eight-path entry-authorization scope, and no later block exists. A ledger
block is therefore an established option for a P01-04D governance package rather
than a universal requirement, and omitting it here leaves the single live
current-state owner intact and unmodified.

Adding a ledger block, or updating any existing canonical record, would require a
separate founder scope disposition. Neither is performed by this package.

## 2. Acceptance criteria

### 1. MODEL A′ named exactly; MODEL A superseded

`MODEL A′` is named exactly and consistently. `MODEL A` is explicitly recorded as
superseded for the activation mechanism, together with the specific superseded
requirement of a canonical activation-record commit following the
execution-authorization merge. No document in this package presents `MODEL A` as
the current activation mechanism.

### 2. No future merge identity in the authorization candidate

The rule prohibits the future execution-authorization package from predicting,
fabricating, reserving or embedding its own future merge commit identity. No
document in this package presents any unresolved future merge identity as a real
value, and none is written in any form.

### 3. Required bindings of the future execution authorization

The future execution authorization must bind:

```text
reviewed pre-adoption baseline
exact candidate tree
exact authority scope
activation verification requirements
```

### 4. Required establishments of the post-merge verifier

The post-merge verification must establish:

```text
actual merge commit
actual merge tree
ordered parents
candidate-to-merge tree equality
required checks successful
formal operator identity
runtime identity
execution-input-manifest identity
external-evidence-harness identity
all remaining execution bindings defined by the authorization
```

### 5. Verified merge becomes the expected canonical commit

On a passing verification, and only then, the verified execution-authorization
merge commit becomes the exact value supplied as `--expected-canonical-commit`.

### 6. No second canonical commit

The verification creates no second canonical commit and none may be required
merely to bind the resolved activation identity.

### 7. Failed verification leaves execution unauthorized

A failed verification activates nothing, supplies no expected canonical commit,
is never partially honoured, and returns the matter to founder disposition.

### 8. Canonical main movement invalidates activation

The package records exactly:

```text
CANONICAL MAIN MOVEMENT AFTER ACTIVATION VERIFICATION:
INVALIDATES ACTIVATION;
NEW FOUNDER-GOVERNED DISPOSITION OR RE-VERIFICATION REQUIRED BEFORE EXECUTION
```

No automatic reactivation, implicit re-pinning or silent continuation is defined
anywhere. Where existing canonical policy is stricter, the stricter policy
controls.
